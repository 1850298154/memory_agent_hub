在工业级 RAG 系统中，单纯的一张 `documents` 表是不够的。为了支持**多知识库（Multi-Knowledge Base / Libraries）**、**文件管理**以及**切片（Chunk）溯源**，我们需要设计一个 **三层架构** 的数据库模型。

这三层通常是：
1.  **知识库 (Knowledge Base / Library)**：逻辑分组，比如 "HR政策"、"IT文档"。
2.  **源文件 (Source Document)**：实际上传的文件，比如 "员工手册.pdf"。
3.  **文档切片 (Document Chunk)**：真正用于检索的文本块，包含向量和关键词索引。

```mermaid
    B -->|1:N| C[document_chunks (切片/索引表)]
    
    %% 核心检索发生在 C 表，但需要 A 表做权限/范围隔离
```

### 2. PostgreSQL 表结构 SQL 实现

请按顺序执行以下 SQL。这套设计支持**多库隔离**、**元数据过滤**和**混合检索**。

#### Step 1: 启用扩展
```sql
CREATE EXTENSION IF NOT EXISTS vector;
-- 如果你需要中文分词，确保装了 zhparser，否则用 simple 配置
-- CREATE EXTENSION IF NOT EXISTS zhparser; 
```

#### Step 2: 知识库表 (Libraries)
这是最顶层，用于管理不同的库名。
```sql
CREATE TABLE knowledge_bases (
    id bigserial PRIMARY KEY,
    name varchar(255) NOT NULL,          -- 库名，例如 "财务部文档"
    description text,                    -- 描述
    created_at timestamptz DEFAULT now(),
    
    -- 索引：按名字查询
    UNIQUE(name) 
);
```

#### Step 3: 源文件表 (Source Documents)
记录文件层面的信息，比如文件名、哈希值（去重用）、上传状态。
```sql
CREATE TABLE source_documents (
    id bigserial PRIMARY KEY,
    kb_id bigint REFERENCES knowledge_bases(id) ON DELETE CASCADE, -- 归属哪个库
    
    file_name varchar(255) NOT NULL,     -- 文件名 "report.pdf"
    file_hash varchar(64) NOT NULL,      -- MD5/SHA256，用于文件级去重
    file_type varchar(50),               -- pdf, docx, txt
    meta_info jsonb,                     -- 额外元数据 (上传人, 原始URL等)
    
    created_at timestamptz DEFAULT now(),
    
    -- 索引：加速按库查询文件
    CONSTRAINT fk_kb FOREIGN KEY(kb_id) REFERENCES knowledge_bases(id)
);
CREATE INDEX idx_source_docs_kb ON source_documents(kb_id);
CREATE INDEX idx_source_docs_hash ON source_documents(file_hash);
```

#### Step 4: 切片表 (Document Chunks) —— **核心表**
这是实际存储向量和 `tsvector` 的地方。**关键设计点：反范式化 (Denormalization)**。
虽然 `doc_id` 已经关联了 `kb_id`，但我们通常会在这个表里**冗余存储 `kb_id`**。
*   **原因**：检索时 99% 的情况是 `WHERE kb_id = ?`。如果每次检索都要 JOIN `source_documents` 表来判断属于哪个库，性能会非常差。

```sql
CREATE TABLE document_chunks (
    id bigserial PRIMARY KEY,
    doc_id bigint REFERENCES source_documents(id) ON DELETE CASCADE, -- 归属哪个文件
    kb_id bigint REFERENCES knowledge_bases(id) ON DELETE CASCADE,   -- 归属哪个库 (冗余字段，优化查询)
    
    chunk_index int,                     -- 切片在原文中的序号 (第几个块)，用于排序
    content text,                        -- 切片内容
    meta_info jsonb,                     -- 元数据 (页码: {page: 1})
    
    -- 核心检索列
    embedding vector(1536),              -- 向量 (根据模型调整维度)
    tsv tsvector                         -- 关键词索引
);

-- 1. 向量索引 (HNSW)
-- 这是一个部分索引(Partial Index)的思路，如果你的库非常多，可以考虑分区表
-- 这里建立全局 HNSW 索引
CREATE INDEX idx_chunks_embedding ON document_chunks USING hnsw (embedding vector_cosine_ops);

-- 2. 全文检索索引 (GIN)
CREATE INDEX idx_chunks_tsv ON document_chunks USING gin (tsv);

-- 3. 过滤索引 (非常重要！)
-- 当你 WHERE kb_id = 1 时，PG 需要快速定位范围
CREATE INDEX idx_chunks_kb_id ON document_chunks(kb_id);
CREATE INDEX idx_chunks_doc_id ON document_chunks(doc_id);
```

### 3. 如何在“特定库”中进行双路召回？

现在的 SQL 查询需要加上 `kb_id` 的过滤条件。

**场景**：在“财务部文档”库（假设 ID=5）中，搜索 “报销流程”。

```sql
WITH target_kb AS (
    SELECT 5::bigint as kb_id  -- 指定库 ID
),
semantic_search AS (
    -- 1. 向量检索 (限定 kb_id)
    SELECT 
        id, 
        RANK() OVER (ORDER BY embedding <=> '[...向量...]'::vector) AS rank
    FROM document_chunks
    WHERE kb_id = (SELECT kb_id FROM target_kb) -- 【关键】只搜这个库
    ORDER BY embedding <=> '[...向量...]'::vector
    LIMIT 20
),
keyword_search AS (
    -- 2. 关键词检索 (限定 kb_id)
    SELECT 
        id, 
        RANK() OVER (ORDER BY ts_rank_cd(tsv, plainto_tsquery('chinese', '报销流程')) DESC) AS rank
    FROM document_chunks
    WHERE 
        kb_id = (SELECT kb_id FROM target_kb) -- 【关键】只搜这个库
        AND tsv @@ plainto_tsquery('chinese', '报销流程')
    LIMIT 20
)
-- 3. RRF 融合 (不变)
SELECT 
    COALESCE(s.id, k.id) AS id,
    d.content,
    d.meta_info,
    (
        COALESCE(1.0 / (60 + s.rank), 0.0) + 
        COALESCE(1.0 / (60 + k.rank), 0.0)
    ) AS final_score
FROM semantic_search s
FULL OUTER JOIN keyword_search k ON s.id = k.id
JOIN document_chunks d ON COALESCE(s.id, k.id) = d.id
ORDER BY final_score DESC
LIMIT 5;
```

### 4. 为什么这样设计是“工业级”的？

1.  **冗余 `kb_id`**：
    *   在 `document_chunks` 表中多存一个 `kb_id` 字段看起来是冗余，但在千万级数据检索时，这能避免 `JOIN source_documents` 带来的巨大开销。这是一个经典的“空间换时间”优化。
2.  **文件与切片分离**：
    *   `source_documents` 存文件状态（上传中、解析失败、已完成）。如果解析失败，只需要操作 `source_documents` 表，不需要污染 `document_chunks` 表。
    *   删除文件时，利用 `ON DELETE CASCADE`，数据库会自动把该文件对应的 100 个切片全部删掉，保证数据一致性。
3.  **元数据 (JSONB) 灵活扩展**：
    *   `meta_info` 字段可以存 `{"page_number": 12, "author": "张三", "year": 2023}`。
    *   PG 的 JSONB 性能极强，你可以直接对 JSONB 里的字段建索引，实现 `WHERE meta_info->>'year' = '2023'` 的精确过滤。

这一套表结构是目前类似 **Dify**、**FastGPT** 等开源 RAG 平台的底层标准范式。


这是一个非常硬核的需求。为了实现**工业级**的落地，我们不能直接使用 LangChain 自带的 `PGVector` 类（因为它绑定了固定的表结构，无法适配我们设计的高性能三层架构）。

我们需要采用 **"LangChain 接口 + 自定义实现"** 的模式：
1.  **Ingestion（入库）**：手写 Python 代码处理分词、向量化和批量插入，确保数据写入我们设计的三层表。
2.  **Retrieval（检索）**：继承 LangChain 的 `BaseRetriever`，封装我们之前写的 **RRF 双路召回 SQL**。
3.  **Generation（生成）**：使用 LangChain 的 LCEL 语法组装最终链路。

#### Part A: 核心定义与 DB 管理 (Ingestion)

```python
import json
import jieba
import psycopg2
import numpy as np
from typing import List, Dict, Any
from psycopg2.extras import execute_values
from langchain_core.documents import Document
from langchain_openai import OpenAIEmbeddings
from langchain_text_splitters import RecursiveCharacterTextSplitter

# 数据库连接配置
DB_CONFIG = "postgresql://postgres:password@localhost:5432/rag_db"

class RAGKnowledgeBaseManager:
    """
    负责离线链路：建库、上传文件、切片、向量化、入库
    """
    def __init__(self, connection_string: str):
        self.conn_str = connection_string
        self.embeddings = OpenAIEmbeddings() # 假设环境变量已配置 OPENAI_API_KEY

    def create_kb(self, name: str, description: str = "") -> int:
        """创建一个新的知识库"""
        with psycopg2.connect(self.conn_str) as conn:
            with conn.cursor() as cur:
                cur.execute(
                    "INSERT INTO knowledge_bases (name, description) VALUES (%s, %s) RETURNING id;",
                    (name, description)
                )
                kb_id = cur.fetchone()[0]
        return kb_id

    def add_document(self, kb_id: int, file_name: str, text_content: str):
        """
        工业级入库流程：
        1. 存入 source_documents
        2. 切片 (Chunking)
        3. 向量化 (Embedding)
        4. 中文分词 (用于全文检索)
        5. 批量写入 document_chunks
        """
        # 1. 文本切片
        splitter = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50)
        chunks = splitter.split_text(text_content)
        
        # 2. 批量计算向量 (减少网络 IO)
        vectors = self.embeddings.embed_documents(chunks)
        
        with psycopg2.connect(self.conn_str) as conn:
            with conn.cursor() as cur:
                # 3. 写入源文件表
                cur.execute(
                    """INSERT INTO source_documents (kb_id, file_name, file_hash, file_type) 
                       VALUES (%s, %s, %s, 'txt') RETURNING id;""",
                    (kb_id, file_name, "dummy_hash_for_demo") # 实际应计算 MD5
                )
                doc_id = cur.fetchone()[0]
                
                # 4. 准备批量写入的数据
                insert_data = []
                for idx, (chunk_text, vector) in enumerate(zip(chunks, vectors)):
                    # 【关键】应用层分词，解决 PG 默认对中文支持不好的问题
                    # 将 "我爱RAG" 分词为 "我 爱 RAG"，用空格连接适配 'simple' 配置
                    seg_list = jieba.cut(chunk_text)
                    keywords = " ".join(seg_list)
                    
                    # 构造插入元组
                    insert_data.append((
                        doc_id, 
                        kb_id, 
                        idx, 
                        chunk_text, 
                        json.dumps({"source": file_name}), 
                        vectors[idx],     # vector 类型
                        keywords          # 传给 to_tsvector 的文本
                    ))
                
                # 5. 高效批量插入 (Batch Insert)
                # 注意：tsv 列使用了 to_tsvector('simple', %s)
                insert_query = """
                    INSERT INTO document_chunks 
                    (doc_id, kb_id, chunk_index, content, meta_info, embedding, tsv)
                    VALUES %s
                """
                # 我们需要稍微处理一下 VALUES 的格式以适配 execute_values 和 to_tsvector
                # 这里为了简单，我们直接在 Python 里拼好，或者使用专门的 SQL 构造
                # 更稳健的做法是下面这样：
                
                for row in insert_data:
                    cur.execute("""
                        INSERT INTO document_chunks 
                        (doc_id, kb_id, chunk_index, content, meta_info, embedding, tsv)
                        VALUES (%s, %s, %s, %s, %s, %s, to_tsvector('simple', %s))
                    """, row)
                
                print(f"成功入库 {len(chunks)} 个切片到知识库 {kb_id}")
```

#### Part B: 自定义双路召回 Retriever (Retrieval)

这是整个系统的核心。我们继承 LangChain 的 `BaseRetriever`，这样它可以无缝集成到 LangChain 的 Pipeline 中。

```python
from langchain_core.retrievers import BaseRetriever
from langchain_core.callbacks import CallbackManagerForRetrieverRun

class IndustrialPGRetriever(BaseRetriever):
    """
    自定义检索器：实现基于 PostgreSQL 的 RRF 双路召回
    """
    conn_str: str
    kb_id: int
    embeddings: Any
    top_k: int = 5

    def _get_relevant_documents(
        self, query: str, *, run_manager: CallbackManagerForRetrieverRun = None
    ) -> List[Document]:
        """
        核心检索逻辑：SQL 实现 Vector + Keyword + RRF Fusion
        """
        # 1. 准备查询向量
        query_vector = self.embeddings.embed_query(query)
        
        # 2. 准备关键词查询 (Jieba 分词)
        # 将 "如何优化RAG" -> "如何 & 优化 & RAG"
        seg_list = jieba.cut(query)
        # 过滤掉空字符，用 & 连接
        query_keywords = " & ".join([w for w in seg_list if w.strip()])
        if not query_keywords:
            query_keywords = query # fallback
            
        # 3. 执行 SQL (工业级 CTE 写法)
        sql = """
        WITH target_kb AS (
            SELECT %s::bigint as kb_id
        ),
        semantic_search AS (
            SELECT id, RANK() OVER (ORDER BY embedding <=> %s::vector) AS rank
            FROM document_chunks
            WHERE kb_id = (SELECT kb_id FROM target_kb)
            ORDER BY embedding <=> %s::vector LIMIT 20
        ),
        keyword_search AS (
            SELECT id, RANK() OVER (ORDER BY ts_rank(tsv, to_tsquery('simple', %s)) DESC) AS rank
            FROM document_chunks
            WHERE kb_id = (SELECT kb_id FROM target_kb)
              AND tsv @@ to_tsquery('simple', %s)
            LIMIT 20
        )
        SELECT 
            d.content,
            d.meta_info,
            (COALESCE(1.0 / (60 + s.rank), 0.0) + COALESCE(1.0 / (60 + k.rank), 0.0)) AS final_score
        FROM semantic_search s
        FULL OUTER JOIN keyword_search k ON s.id = k.id
        JOIN document_chunks d ON COALESCE(s.id, k.id) = d.id
        ORDER BY final_score DESC
        LIMIT %s;
        """
        
        results = []
        try:
            with psycopg2.connect(self.conn_str) as conn:
                with conn.cursor() as cur:
                    cur.execute(sql, (
                        self.kb_id,
                        str(query_vector), str(query_vector), # 向量用两次
                        query_keywords, query_keywords,       # 关键词用两次
                        self.top_k
                    ))
                    rows = cur.fetchall()
                    
                    for row in rows:
                        content, meta, score = row
                        # 转换回 LangChain Document 对象
                        doc = Document(
                            page_content=content,
                            metadata={**meta, "score": score}
                        )
                        results.append(doc)
        except Exception as e:
            print(f"检索出错: {e}")
            
        return results
```

#### Part C: 组装 RAG Pipeline (Generation)

```python
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnablePassthrough

def run_industrial_rag_demo():
    # --- 1. 初始化与入库 (模拟) ---
    manager = RAGKnowledgeBaseManager(DB_CONFIG)
    
    # 创建库 (如果不存在的话，实际逻辑需判断)
    # kb_id = manager.create_kb("企业IT文档", "存放服务器运维手册")
    kb_id = 1 # 假设已有 KB ID = 1
    
    # 模拟上传文档
    sample_text = """
    RAG系统的双路召回是指结合向量检索和关键词检索。
    PGVector 是 PostgreSQL 的向量插件。
    Redis 的热 Key 问题会导致性能下降。
    """
    # manager.add_document(kb_id, "tech_guide.txt", sample_text)
    
    # --- 2. 构建检索器 ---
    # 实例化我们自定义的 IndustrialPGRetriever
    retriever = IndustrialPGRetriever(
        conn_str=DB_CONFIG,
        kb_id=kb_id,            # 指定只搜这个库
        embeddings=OpenAIEmbeddings(),
        top_k=3
    )
    
    # --- 3. 构建 Prompt 和 LLM ---
    template = """你是一个智能助手。基于以下检索到的上下文回答用户问题。
    如果上下文没有相关信息，请直接说不知道。

    {context}
    
    用户问题: {question}
    """
    prompt = ChatPromptTemplate.from_template(template)
    model = ChatOpenAI(model="gpt-4o-mini") # 或使用 deepseek 等兼容接口

    def format_docs(docs):

    chain = (
        {"context": retriever | format_docs, "question": RunnablePassthrough()}
        | prompt
        | model
        | StrOutputParser()
    )
    
    # --- 5. 执行 ---
    question = "什么是 RAG 的双路召回？"
    print(f"User Question: {question}")

        print(chunk, end="", flush=True)

if __name__ == "__main__":
    run_industrial_rag_demo()
```

### 代码实现的关键点解析

1.  **为什么不直接用 `PGVector.from_documents`?**
    *   标准的 LangChain `PGVector` 只能把数据存到一张扁平表中。
    *   而我们的工业级设计有 `knowledge_bases` -> `source_documents` -> `document_chunks` 三层结构。必须用 `RAGKnowledgeBaseManager` 手写 SQL 来维护这种关系和完整性约束（如外键）。

2.  **Jieba 分词的妙用**
    *   在 `RAGKnowledgeBaseManager` 入库时：`keywords = " ".join(jieba.cut(text))`。
    *   在 `IndustrialPGRetriever` 检索时：`query_keywords = " & ".join(...)`。
    *   配合 `to_tsvector('simple', ...)`，我们成功在不依赖数据库插件（`zhparser`）的情况下，实现了对中文的精确分词检索。这是工程上兼容性最好的方案。

3.  **自定义 Retriever**
    *   通过继承 `BaseRetriever`，我们把极其复杂的 **CTE SQL + RRF 逻辑** 封装在了黑盒里。
    *   对于上层的 LangChain LCEL 链来说，它只是一个普通的 Retriever，输入 Query，输出 List[Document]，完全解耦。

4.  **RRF 的 SQL 实现**
    *   代码中的 SQL 使用了 `WITH` 子句并行查询，然后 `FULL OUTER JOIN`，并处理了 null 值（用 `COALESCE`），最后直接在数据库层算出了 `final_score`。这比把几千条数据拉到 Python 内存里算要快得多。

这套代码是一个可以直接拿到生产环境去改的**骨架**，它解决了最棘手的**多库隔离**和**高性能混合检索**问题。
